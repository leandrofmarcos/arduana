Princípios que guiam a estrutura (antes da pasta)

Antes de falar de diretórios, as regras mentais:

Feature-first (não tipo-first)

Baixo acoplamento

Alta coesão

Lazy loading por feature

Nada de shared virando lixão

Standalone components

Estado isolado por domínio

Se a estrutura respeita isso → escala.

📁 Estrutura recomendada (Angular moderno)
src/
└── app/
    ├── core/
    ├── shared/
    ├── features/
    ├── app.routes.ts
    └── app.config.ts


Agora vamos destrinchar com responsabilidade.

🧠 core/ – infraestrutura da aplicação

👉 Tudo que existe uma única vez.

core/
├── auth/
│   ├── auth.service.ts
│   ├── auth.guard.ts
│   └── auth.interceptor.ts
├── http/
│   ├── api.service.ts
│   └── http-error.interceptor.ts
├── layout/
│   ├── shell.component.ts
│   ├── header.component.ts
│   └── footer.component.ts
├── config/
│   └── app-settings.ts
└── core.providers.ts

Regras do core

✔ Singleton
✔ Nunca importar core dentro de feature
✔ Só o app.config.ts importa

Pense no core como infra / fundação.

🔁 shared/ – reutilizável, mas burro

👉 Código sem regra de negócio.

shared/
├── components/
│   ├── button/
│   ├── modal/
│   └── table/
├── directives/
│   └── autofocus.directive.ts
├── pipes/
│   └── date-format.pipe.ts
├── ui/
│   └── icons/
└── shared.imports.ts

Regras do shared

✔ Sem services com lógica
✔ Pode ser importado por qualquer feature
✔ Componentes puros

Se começar a ter regra de negócio → não é shared.

🚀 features/ – onde a aplicação vive

Aqui está o coração da aplicação.

features/
├── orders/
│   ├── pages/
│   │   ├── order-list.page.ts
│   │   └── order-detail.page.ts
│   ├── components/
│   │   └── order-card.component.ts
│   ├── services/
│   │   └── orders.service.ts
│   ├── store/
│   │   ├── orders.store.ts
│   │   └── orders.selectors.ts
│   ├── models/
│   │   └── order.model.ts
│   ├── orders.routes.ts
│   └── index.ts

Regras de ouro das features

✔ Tudo relacionado à feature fica junto
✔ Feature é autônoma
✔ Pode ser lazy loaded
✔ Pode ser apagada sem quebrar o resto

🧩 Lazy Loading (obrigatório em app grande)
export const routes: Routes = [
  {
    path: 'orders',
    loadChildren: () =>
      import('./features/orders/orders.routes')
        .then(m => m.ORDERS_ROUTES)
  }
];


Em app grande, tudo que é feature é lazy.
Sem exceção.

📦 Standalone Components (Angular 15+)

📌 Nada de NgModule pra feature.

@Component({
  standalone: true,
  selector: 'order-list',
  imports: [CommonModule, OrderCardComponent],
  templateUrl: './order-list.page.html'
})
export class OrderListPage {}


✔ Mais legível
✔ Menos boilerplate
✔ Mais fácil de testar

🧠 Estado: por feature (não global por padrão)

Evite Redux global gigante.

Opções modernas:

Signals

Component Store

NGXS por feature

Service + Signals

@Injectable()
export class OrdersStore {
  private orders = signal<Order[]>([]);

  readonly orders$ = computed(() => this.orders());

  load() {
    this.orders.set([...]);
  }
}


Estado global só quando realmente global (auth, theme).

🧪 Testes organizados por domínio
orders/
├── services/
│   └── orders.service.spec.ts
├── pages/
│   └── order-list.page.spec.ts


✔ Testa regra
✔ Testa comportamento
✔ Não testa Angular internals

🚫 Anti-padrões clássicos (fuja disso)

❌ shared/services/anything.service.ts
❌ utils/ gigante
❌ pasta models global
❌ services reutilizados entre features diferentes
❌ imports cruzados entre features

📐 Visão mental correta
App
├── Infra (core)
├── UI genérico (shared)
└── Domínios independentes (features)


Isso é DDD aplicado ao frontend, sem misticismo.

⚖️ Comparação rápida
Abordagem	Escala	Manutenção
Tipo-first (components/ services/)	❌ ruim	❌ caos
Feature-first	✅ ótima	✅ limpa
Monolito de estado	❌ ruim	❌ frágil
Estado por feature	✅ ótima	✅ previsível
🧠 Regra final (pra você guardar)

Se uma pasta não representa um domínio da aplicação, ela provavelmente está errada.
